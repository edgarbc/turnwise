# Training Data and Review Contract

This document defines the proposed data contract for the open-weight decision-model experiment. The canonical task and annotation semantics remain in [`configs/tasks/repair-intake.yaml`](../../configs/tasks/repair-intake.yaml) and [`docs/annotation-guide.md`](../annotation-guide.md). If this document conflicts with either, stop export and resolve the discrepancy before generating training rows.

## Row Unit and Identity

One training row represents one annotated transcript prefix, not one complete conversation. A row is identified by the task ID and version, conversation ID, snapshot ID, and the event ID through which the snapshot is annotated. All prefixes from a conversation remain together in one split and are treated as correlated observations in analysis.

The row has three Unsloth fields:

| Field | Contract |
| --- | --- |
| `state` | The inference-time input for this prefix: task/conversation identity, visible transcript events, and candidates extracted only from those events. |
| `questions` | The six task questions and the exact options available to the model for this prefix. |
| `gold` | One valid option key for every question, derived from the reviewed snapshot. |

Keep provenance such as split, snapshot ID, task version, and source hashes as exporter/manifest metadata, not as label text or hidden answer content in `state`.

## State Construction

Construct the state through the same prefix assembly and candidate extraction used by Turnwise inference. Its structure follows the current Jev adapter:

```json
{
  "conversation_id": "repair-004-corrections",
  "task_id": "repair_intake",
  "task_version": "0.1.0",
  "transcript_prefix": [
    {"event_id": "repair-004-e01", "speaker": "customer", "text": "..."}
  ],
  "candidates": [
    {"candidate_id": "repair-004-e01:appliance:4:16", "field_id": "appliance", "text": "refrigerator"}
  ]
}
```

The transcript contains events at or before `through_event_id`, in source order, with event IDs, speaker roles, and text. The candidate list contains all candidates produced for that prefix, in deterministic source order, including distractors. Candidate IDs and spans must be generated by the shared extractor; never hand-author IDs or add future-turn candidates. Timestamps and gold annotations are not part of this state unless the shared provider contract is deliberately revised for every compared system.

Question construction must be extracted from the Jev adapter and reused by export. This preserves the task instructions and exact per-prefix option keys between Jev inference and local training. A question change is a task/experiment change and must be versioned and tested against both paths.

## Question and Gold Mapping

All six fields are present for each row. Question IDs use `value__<field_id>`. Every gold answer is a string option key available in that row's question criteria. The final answer/value normalization still happens in Turnwise code after model selection; training does not teach free-form JSON generation.

### Candidate-backed fields

The candidate-backed fields are `appliance`, `location`, `preferred_appointment`, and `spending_limit`. For each field, criteria contain every candidate ID for that field and its source text, plus the `__unknown__` option.

For a known annotation, find the unique candidate that both:

1. belongs to the annotated field;
2. has the same source event as an annotation evidence reference, and its complete half-open source span is contained within that evidence span; and
3. normalizes through Turnwise's existing normalization function to the annotated value.

The candidate ID is the gold answer. Evidence is essential: matching only a normalized value can select a distractor or an earlier superseded mention. If no candidate satisfies the annotation, report a candidate-extraction/label-mapping failure. Do not map it to `__unknown__`. If more than one candidate remains valid after evidence matching, treat the row as ambiguous and resolve the annotation/mapping rule before export. Do not treat mere span overlap as sufficient support.

If the annotation is null, use `__unknown__` only when the visible prefix contains no supported known value under the task rules. If a known value is stated but extraction omitted it, this is an extraction failure, not an unknown.

### Boolean fields

The boolean fields are `active_leak` and `quote_required`. For every customer event in the visible prefix, provide `true::<event_id>` and `false::<event_id>` choices, described with the field's task criteria and that event's text, plus `__unknown__`. Intake-agent events never provide evidence choices.

For a known annotation, use its boolean value and the event ID from the reviewed evidence reference, yielding `true::<event_id>` or `false::<event_id>`. A missing, non-customer, future, or otherwise invalid evidence event is a data error. For a null annotation, use `__unknown__`; this covers unstated, ambiguous, or conflicting states as specified by the task definition.

### Required completeness

Every row has exactly the six task question IDs in `gold`, and every answer is available in the corresponding question's options. Unknown remains a deliberate class, not a missing label. Do not drop a field just because it is unknown.

## Split and Leakage Policy

Assign scenario families to splits before generating dialogue wording. A family groups scenarios that share the same underlying fact pattern or decision shortcut; paraphrases and close variants belong to the same family. Keep a family, conversation, every prefix, and any later transcript/audio variant derived from it in one split. The split unit is the family, with conversation membership recorded in the manifest.

The working allocation is 30/5/5/10 conversations:

| Split | Proposed conversations | Permitted use |
| --- | ---: | --- |
| Training | 30 | Gradient updates |
| Validation | 5 | Error diagnosis and checkpoint/settings selection |
| Calibration | 5 | Exploratory confidence and abstention calibration, separate from gradient updates |
| Final test | 10 | One frozen comparison after configuration selection |

These totals sum to the initial budget of 50 new conversations. Family assignments and the ten development specifications are recorded in [`data/scenarios/catalog.yaml`](../../data/scenarios/catalog.yaml). That catalogue reserves test-family IDs and counts but withholds test specifications and labels from development. Report conversation counts alongside prefix counts. Do not claim that prefixes are independent samples. Five-conversation validation and calibration estimates, and a ten-conversation test, are exploratory and should include uncertainty and limitations.

Keep the existing 30-conversation pilot in a separate regression partition; it is not eligible for training, validation, calibration, or the new final test. Do not inspect final-test labels during model, threshold, or checkpoint selection. Prefer generating and fully reviewing test data after the workflow and configuration are frozen. If test examples must be created earlier, keep their labels access-controlled and unused in development.

## Review and Provenance

Record provenance and review status at scenario, conversation, annotation/snapshot, and split level, or by linked metadata that unambiguously covers each level. At minimum, record:

- stable IDs and source/specification version;
- assigned family and split;
- generation method/model/version where applicable;
- review level (`unreviewed`, `targeted`, or `full`), reviewer, review date, and outcome;
- annotation/task version and source-file hashes;
- any flags, adjudication, or correction history.

The first reviewed development batch is intended to test the generator and annotation process; do not include final-test labels in that development review loop. After refining the instructions, generate remaining conversations only after family split assignment. Fully review every final-test conversation, selected prefix label, and evidence reference before freezing its hashes.

## Export and Acceptance Checks

The exporter and dataset validator must reject or clearly report:

- task ID/version or field-set mismatches;
- a snapshot cutoff that is absent from its conversation or a state containing events after the cutoff;
- candidate IDs/options that differ from the shared extractor output;
- a known candidate-backed gold value with no unique evidence-supported matching candidate;
- a known boolean without a valid customer evidence event in the visible prefix;
- a gold option that is absent from the corresponding question;
- missing or extra question/gold keys;
- unknown labels that conceal candidate extraction failures;
- unreviewed or disallowed examples in a requested split;
- family/conversation/prefix leakage across splits;
- changed source hashes after a split or test set has been frozen.

The export must be deterministic for identical inputs, task version, and exporter version. Produce a small inspectable sample for review before any training run. Validation success establishes structural consistency, not that a synthetic transcript or label is semantically correct; human review remains required.
